Late invoice, one tap,
paid and booked.

A late invoice becomes a Telegram message. One tap sends the customer a Mollie link; when it is paid, the books already say so.
The demo
Four steps on sandbox data in two minutes — fetch, approve, pay, book back. The last step, the write-back, is the one the program is built around.
The ladder
Five stages, each a runnable program with its own tests; the composed demo falls out at the top.
The plan
Three phases, eleven steps, a named risk beside every step, one port to the books, one hygiene gate before the first upload.
Plate 02 · The problem

A late invoice is a loop of small steps, and each one can go wrong.

Chasing a payment means opening the bookkeeping, finding the invoice, deciding whether this customer deserves a nudge today, writing it, and later checking whether it worked. Each existing answer removes one of those steps and leaves the rest.

Chase by hand
Every step is a decision the owner makes in the bookkeeping, on a laptop, after hours. The decision is good; the cost is that nothing happens on the days there is no laptop.
·
Automatic reminders
Moneybird can send them all. The owner loses the per-customer call — the client who is always late but always pays gets the same letter as the one who has gone quiet.
·
A payment link alone
A link gets money in, and then someone still has to book it. Without the write-back the invoice stays open in the books while the bank says otherwise.
The gap is small and specific: a per-customer decision, made from a phone, that ends with the books already correct. That decision and that write-back are the whole scope of the program.

Plate 03 · The idea

The script holds the state; the owner holds the tap.

One split, load-bearing everywhere. What a script can hold without error — which invoice is late, which proposal was already sent, which link exists, whether a payment was already booked — it holds in one table with one row per invoice. What must stay a human act — sending anything to a customer — is a button the owner presses.

The script holds
A SQLite table actions, unique on invoice_id, with a status that only moves forward: pending → approved or rejected → link_created → booking → paid. Run it twice and nothing doubles: no second message, no second link, no second booking; amounts are integer cents, never a float. It reaches the books through one four-verb port; the stages never learn which package stands behind it.
•
The owner holds
The keys (three of them, in a local .env that never enters the repo), the sandbox and its fake invoices, and the tap itself — Goedkeuren or Afwijzen — checked against the owner's own chat id and user id before anything moves.
The split decides the design. Every guard on the next plates protects one of the two halves: the state the script holds, or the tap the owner keeps.

Plate 08 · The five stages

Each stage is done when it runs on its own and its test went red first.

Stage 1 · in progress
Fetch late invoices
The port, the Fake and Moneybird adapters, the money formatter, the actions table. Done when a second run adds no rows, a float is refused, and both adapters pass one contract test.
Stage 2 · test first
Telegram approval
One message per pending row, two buttons, chat-id and user-id check; the bot owns the event loop. Done when a tap changes the status, a foreign chat is ignored, and a stale tap changes nothing.
Stage 3 · test first
Mollie test link
Re-check open, create the link, send it back; three tries with a growing wait, then cancel. Done when a paid invoice yields no link, a second tap no second link, and a timeout after the POST no second link.
Stage 4 · test first
Check and write back
Poll the link until it is paid; re-read the invoice, match the open amount, then book through the port. Done when running twice books once and an invoice paid elsewhere is reported, not booked.
Stage 5 · reviewed
The composed demo
One entrypoint, a log line per step, the done-checklist walked. Done after three clean runs in a row and a clean secret scan of the whole history.
The whole test suite is written before stage 1 and committed red: the zero point. Each stage turns its own slice green and never deletes a red test to get there. A check that never failed has only been inspected, not verified.

Plate 10 · The public repo

Born with its gitignore, licensed MIT, one package, a module per stage.

Written locally, uploaded by the owner to a public repository — only once the hygiene floor passes. Nothing reaches the repository before the secret scan and the tree check are clean.

Layout

common/ — the shared parts; adapters/ — moneybird · fake + sample data

•
Secrets discipline
.env and every .env.* ignored, .env.example allowed back in with empty values. Test keys only: a Mollie test_ key moves no money; a bot or Moneybird token still reads the sandbox. A leaked key is rotated; history keeps it.
MIT. The record of how it was built — the plan, the rules, every log and report — sits in the repository beside the code.

Plate 11 · The main rules

Three main rules; every guard in the plan descends from one.

The rules the plan started with and the guards inside the steps are not the law. They are instances of three rules named at the review. A guard that fits none of the three is a signal to stop and ask why it exists.

1 · Safety and security
The demo touches money and a customer list. Nothing moves unless it is safe to move; in doubt, it does not move. Secrets never in the repo · a payment booked once · fail closed · money as integer cents · the double-payment guard · token scope · callback checks · the hygiene floor before upload.
·
2 · Transparency and traceability
What happened, and why, must be readable from the record alone — code, logs, repo, plan. One log line per step with who, what, when and the row · a forward-only state machine · API-NOTES.md with read dates · the plan projected into the repo · the zero-point test baseline · one log per build round.
·
3 · Efficiency and design
Small parts that run alone, one way to do each thing, nothing the demo does not need. Each stage runs on its own · one port, adapters behind it · one money formatter · one retry policy · one module per stage, one package, one command · the scope rule · fake data only.
